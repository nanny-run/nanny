title: Deploying a governed app
description: Run a Nanny-governed app in a container or on a server. One command, one secret, and nothing to carry between deploys.
---

## The shape

A deployed Nanny app is one process:

```dockerfile
CMD ["nanny", "run", "--serve", "--", "discord"]
```

`--serve` starts the governance server and launches your `[start].cmd` underneath it. Trailing arguments append to that command, exactly as with plain `nanny run`.

<Note>
  **Always deploy with `--serve`, even for a single process.** It is the only
  shape verified against a real container, a real port, and a real restart, so
  it is the one guaranteed to behave the same on every platform. Plain
  `nanny run` still works and stays the right choice for local development
  (see [Quickstart](/v0.6/quickstart)), but production always means `--serve`.
</Note>

There is no login step and no state to carry between deploys. A fresh container behaves the same as one that has been running for a month, and twenty replicas behave the same as one.

A governor writes a few files recording its own address, pid and token so that other processes *on the same machine* can find it with `--join`, `status` and `stop`. None of that is required: where the directory is not writable, it says so once and serves anyway, so a read-only root filesystem runs a governor perfectly well. A process joining from another machine is given the address and token as configuration and never reads them.

## One secret

```bash
NANNY_API_KEY=nny_...
```

Create it in the dashboard under **Settings → API Keys**, then set it however your platform sets secrets: a Fly secret, a Kubernetes `Secret`, a Coolify environment variable. That single variable decides whether runs sync; see [Connect to Nanny Cloud](/v0.6/guides/managed-mode).

The key's prefix (`nny_live_` or `nny_sdbx_`) also decides whether this deployment writes real evidence or throwaway sandbox data, see [Live and sandbox](/v0.6/guides/environments) before deploying against a live key for the first time.

Leave it unset and everything still works. Enforcement is local and never depends on the cloud.

<Warning>
  Do not bake the key into an image or commit it. It is an ordinary deployment
  secret and belongs with the rest of them.
</Warning>

## Which command to use

**In production, every row below starts with `--serve`.** The only question is
whether it launches your process directly or a second process joins it.

| Your situation | Command |
| --- | --- |
| One app, one process | `nanny run --serve` |
| Several processes under one rule set | `nanny run --serve` (governor) + `nanny run --join=<appId>` |
| A governor with no app of its own | `nanny run --serve` with no `[start]` |

## Ports

The governor binds `127.0.0.1:62669` by default. If that port is taken it steps to the next free one and says so, then records the real address where `--join` and `nanny status` look for it, so several apps can run on one machine without configuration.

Pass `--addr` only when the governor must be reachable from another machine. A non-loopback address makes mTLS mandatory and requires a certificate bundle (`nanny certs generate`). If a port you named explicitly is busy, that is an error rather than a silent move to a different one. A governor listening somewhere the firewall does not expect is worse than one that refuses to start.

## Signals and shutdown

Run `nanny` as PID 1 (a plain `CMD`, not wrapped in a shell). It receives `SIGTERM` directly, drains connections for up to 10 seconds, and stops the app it launched. If the app exits, the governor shuts down with it.

A shell wrapper breaks this: `sh` does not forward signals to its children, so the governor never drains, and nothing notices if one half dies while the other keeps running half-governed.

## Dependencies and the allowlist

Install dependencies at build time rather than at start time, so a governed run does not fail on something unrelated to its policy:

```dockerfile
RUN uv sync --locked        # or pip install -r requirements.txt, npm ci, …
```

This is working as intended, since the allowlist is doing its job, but it is a surprising way to discover it, so it is worth getting right before the first deploy.

<Warning>
  `--locked`, not `--frozen`. Both refuse to update the lock file; only
  `--locked` first checks that the lock still agrees with `pyproject.toml`.
  With `--frozen`, a lock left behind by an edited `pyproject.toml` installs
  anyway, so an image can ship an older `nanny-sdk` than the one you asked
  for and fail at runtime on a symbol that exists in the version you thought
  you had. `npm ci` and `pip install -r` already fail this way by default.
</Warning>

## Checking it worked

```
nanny: mode managed, syncing to https://api.nanny.run (app: your-app)
nanny: governance server started
  address      : 127.0.0.1:62669
  session token: 34e6beee…8fad (64 chars)
  token file   : /root/.nanny/servers/app_…/server.token
nanny: running [start] under this governor (plain HTTP, loopback)
```

The token is printed as a fingerprint, never in full: eight characters from the
head, four from the tail, and the length. That is enough to confirm the governor
took the token you set and not a stale one, and not enough to use, so a log
aggregator holding it forever costs you nothing. The full value is in the token
file named on the line below it. Under mTLS the governor also prints the
variables a joining process needs.

Then `nanny status` from the same directory, or the dashboard, which lists the app by the name in `.nanny/app.json`.

If the cloud is unreachable, events are held under `.nanny/spool/` (partitioned by environment) and delivered on the next run. See [Connect to Nanny Cloud](/v0.6/guides/managed-mode). If your platform gives the container a writable filesystem this is automatic; if it does not, a cloud outage costs those events, and everything else still works.
