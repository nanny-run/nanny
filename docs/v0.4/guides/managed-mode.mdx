## What managed mode does

By default, Nanny runs **local-only**: it enforces your limits and rules on your machine and writes an event log to stdout. Nothing leaves the box.

**Managed mode** keeps enforcement exactly where it is — local, deterministic, offline-capable — and *additionally* forwards a copy of your run's event log to [Nanny Cloud](https://nanny.run). In return you get, per organization:

- A dashboard of every run — steps, tokens, stop reasons, models
- Spend and usage trends across all your agents
- Alerts when a run starts to spiral
- A durable, exportable audit trail (compliance tiers)

Enforcement never depends on the network. If the cloud is slow or unreachable, your agent runs exactly as it would locally — forwarding is best-effort and never blocks or fails a run.

<Note>
  Managed mode is **additive**. It changes nothing about how limits and rules are
  enforced — only whether a copy of the event log is sent to your dashboard.
</Note>

## Turn it on

Two steps, and neither puts a secret in your config.

**1. Say this project wants the cloud** — set the mode in `nanny.toml`:

```toml
[runtime]
mode = "managed"
```

**2. Connect this machine** — log in once (opens your browser to approve, and picks your org there):

```bash
nanny auth login
```

That stores an ingest-only key in `~/.nanny/credentials.toml` — this machine only, never your repo. Now run as usual:

```bash
nanny run python agent.py
```

Your run appears in the dashboard within a few seconds of finishing. No code changes, no per-call instrumentation, and **no endpoint or key in `nanny.toml`**.

<Note>
  Sync needs **both** halves, and they live in different places on purpose: the
  intent (`mode = "managed"`) is committable config, and the credential
  (`nanny auth login`) is stored outside your repo. So a local-mode project never
  syncs even while you are logged in, and a machine that never logged in never
  syncs even in managed mode.
</Note>

## CI and headless machines

A browser flow needs a person. For CI or a headless box, log in with a pre-minted ingest key instead of the browser — the key comes from `NANNY_API_KEY` (a CI secret) or stdin, never a command argument:

```bash
NANNY_API_KEY="nny_..." nanny auth login --token --env prod
# or:  echo "$NANNY_API_KEY" | nanny auth login --token --env staging
```

This writes the same `~/.nanny/credentials.toml` without opening a browser. `--env` is required so the machine targets the right cloud (log in once on a laptop to mint the key, then drop it in your CI secrets).

## Skip a single run

Forward nothing for one run, without logging out:

```bash
nanny run --no-sync python agent.py
```

## Local vs managed

|                          | `mode = "local"` (default) | `mode = "managed"` + logged in         |
| ------------------------ | -------------------------- | -------------------------------------- |
| Enforcement             | Local, deterministic       | Local, deterministic (unchanged)       |
| Event log               | stdout / file              | stdout / file **+** forwarded to cloud |
| Network required to run | No                         | No (forwarding is best-effort)         |
| Dashboard & trends      | —                          | Yes                                    |

<Warning>
  In managed mode with no login, Nanny prints a one-time nudge and keeps enforcing
  **locally** — it just won't forward. Run `nanny auth login` to connect.
</Warning>

## Turning it off

- **One run:** `nanny run --no-sync`.
- **This machine, for good:** `nanny auth logout` (deletes the local credential; the key still exists in the cloud until you revoke it from the dashboard).
- **This project:** set `mode = "local"` in `nanny.toml`.
